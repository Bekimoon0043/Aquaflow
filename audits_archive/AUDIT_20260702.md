# AquaFlow Studio — Codebase Audit vs Product Strategy

_Date: 2026-07-02_

**Method:** static review of the actual `aquaflow/frontend/src` and `aquaflow/backend` trees (file/line evidence cited). Not run against live hardware. `◑` = judgment call, explained. `.venv` matches excluded.

---

## MODULE 1 — Fountain Designer → **~40%**

| Item | Status | Evidence / gap |
|---|---|---|
| Pool geometry: rectangular / circular / freeform / irregular | ✅ | `PoolGeometryDesigner.jsx` handles rectangular, circle, ellipse, freeform, polygon |
| Pool geometry: multi-pool | ❌ | no multi-pool code |
| Pool geometry: elevation / tiered | ❌ | no elevation/tier support |

| CAD output — DXF/DWG, IFC/BIM, PDF drawings, pipe isometrics | ❌ | **zero matches** for dxf/dwg/ifc/bim/isometric/pdf anywhere in the codebase |

**Reality:** a solid design canvas + fixture placement + BOM, but not a CAD tool — no drawing export at all, and the library is 14% of target.

## MODULE 2 — Hydraulic Engineer → **~12%** (weakest module)

| Item | Status | Evidence / gap |
|---|---|---|
| Pressure loss (Hazen-Williams / Darcy-Weisbach) | ❌ | `hydraulicEngine.js:79` uses `frictionHeadM = totalFlowM3Hr * 0.05` — a fabricated linear approximation. No H-W, no D-W, no Colebrook |
| DN sizing by velocity rules | ◑ | crude flow→pipe lookup table (`recommendedPipeMm`), not per-pipe velocity |
| Pipe network auto-routing + obstacle avoidance | ◑ | manual pipe drawing exists (`usePipeDrawing.js`, 842 lines); **no** auto-route/pathfinding/obstacle code |
| Real-time validation (R/Y/G) | ◑ | pump `OK/UNDERSIZED/NO_PUMP` flags + DiagnosticsPanel indicators |
| Energy consumption modelling | ◑ | `hydraulicPowerKw` computed; no real duty model |
| Wind drift | ◑ | one line: `wind_speed_ms * 0.3` in `CalibrationPanel.jsx:168` |
| Minor losses · Multi-zone isolation · Pump-curve import · System-curve/operating-point · VFD calc · Parallel/series pumps · NPSH · Freeze-protection sizing · Water-treatment sizing · Carbon footprint | ❌ | none exist. ("co2" in code = CO₂ for fog/flame effects, not carbon footprint; "freeze" = a signal type, not sizing; "VFD" = device label + an AI suggestion string) |

**Reality:** this is a **load-aggregation calculator**, not a hydraulic engineering module. 14 of 16 capabilities absent.

**Phase 3 (Year 3):** ❌ entirely.

## 3 · Top 10 priorities for Stage 1 — *"run a complete show at a real LuxuryCon site"*

Stage 1 is about **execution on real hardware**, not CAD/hydraulic depth. Ordered by critical path:

| # | Priority | Why it's Stage-1 critical | Effort |
|---|---|---|---|
| 1 | **Make the backend fixture-aware** — extend show payload/`show_engine.get_snapshot()` to carry `fixtures`+`groups`; drive `protocol_bus` from designed fixtures, not the 10 seed devices | Today a designed show **cannot reach real hardware** — the runtime only knows seed devices (architecture-review #3/#7) | **Large** |
| 2 | **Automatic DMX/protocol address assignment** (fixtures → universe/channel, Modbus register) | Real fixtures need real addresses to output; currently manual/absent | **Medium** |
| 3 | **Hardware conflict detection** (duplicate address/channel/universe) | Prevents silent mis-wiring at the site | **Small–Medium** |
| 4 | **Verify protocol output on real/simulated hardware** — Art-Net + Modbus at the 100 Hz loop; confirm sACN/Modbus drivers actually emit | Never validated against hardware; this *is* Stage 1 | **Large** |
| 5 | **Multi-universe beyond 4** (`protocol_bus.py` caps at 4) + wire real audio file → beat markers end-to-end (install numpy/librosa path) | Real sites exceed 4 universes; a real track must drive the show | **Medium** |
| 6 | **Compile → deploy bundle → on-site playback verified** (`luxshow_compiler` + `runtime_exporter` exist but unproven end-to-end) | The delivery mechanism for the show | **Medium** |
| 7 | **Safety-limit enforcement in the runtime/output path** (clamp per-fixture intensity/pressure before emit) | Non-negotiable before driving water/flame at a live venue | **Medium** |
| 8 | **Cue-stack / Go-based operator playback + scene recall** | How an operator actually runs the show live on site | **Medium** |
| 9 | **Automated + hardware-in-the-loop test harness** (there are **no tests** today) | A hardware/safety system must not go live untested | **Medium** |
| 10 | **Unattended-ops essentials: fault alerting (email/SMS) + maintenance log** | Scheduled shows run unattended; operators need to be told when something faults | **Medium** |

## Honest caveats

- This is static analysis; I did **not** run against live hardware, so #4-class items ("does it actually emit correct DMX?") are unverified either way.
- `◑` scores involve judgment — I erred toward honesty (e.g., a timecode *enum* is not MIDI sync; a `flow × 0.05` line is not Hazen-Williams).
- **Deliberately excluded from Stage-1 top-10** (real, but not on the "run a show" critical path): the hydraulic engine rebuild (Module 2), CAD export (Module 1), and the 500+ fixture library expansion — these matter for *selling/designing* installations, not for *running* the first show.
